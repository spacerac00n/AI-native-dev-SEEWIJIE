# Failure investigation

Guide the coding agent during development. Diagnose observed evidence; do not let AI independently assign a test verdict.

1. Read [EXECUTION.md](../../../docs/EXECUTION.md) and the relevant requirements in [PRODUCT.md](../../../docs/PRODUCT.md). Identify the run ID, plan/revision/hash/approval, tested commit and dirty flag, command, exit code, and discovered/executed/passed/failed/skipped counts. Start with `data/runs/<run-id>.json` and `artifacts/executor/<run-id>/run.json`; a rejected or interrupted attempt may instead have only `attempt.json`, `rejection.json`, or partial logs. Missing results are not passes.
2. Preserve the original record and complete artifact directory before changing code, test definitions, or configuration. Retain the plan/approval snapshot and tested SHA. Never replace, delete, relabel, or backfill failed evidence; report missing captures honestly. Use new run IDs for retests.
3. Read `playwright.json`, `stdout.log`, `stderr.log`, and each affected case's `result.json` and `observation.json`. Compare the first failed assertion's definition, expected/actual values, error, and phase; later assertions may never have executed. Inspect indexed screenshots and `cases/<case-id>/browser-api.log.json` for rendered state, request failures, and actual API assertion responses. Open an available trace with `npx playwright show-trace <trace-path>` and examine action timing and network responses. Screenshots alone may not prove backend persistence. Baseline and dashboard suites retain their own reports under `artifacts/playwright/` and `artifacts/dashboard/`.
4. Separate observations from diagnosis:
   - `assertion-failed`: Playwright observed a mismatch. Determine whether the requirement, expectation, adapter, or product behavior explains it before claiming a product defect.
   - `execution-error`: setup, action, runner, or completion failed. This status does **not** establish an environmental root cause; application crashes, adapter bugs, and logically invalid action sequences can also cause it.
   - Invalid definition or approval rejection: inspect validation/digest/revision errors before execution. Do not report a rejected attempt as executed coverage. Schema-valid definitions can still be semantically wrong.
5. Form a concrete hypothesis and check it against source and evidence. Follow the path through `tests/executor/adapters.ts`, `apps/api/src/executor.ts`, the React demo, and `apps/api/src/demo.ts` as relevant. Check server startup, occupied ports, test-mode controls, and active-run ownership when logs implicate them. Do not remove an active lock or reset a running shared target. Mark unproven causes as hypotheses; claim flaky behavior only from differing outcomes observed across comparable runs.
6. Fix the evidenced cause with the smallest coherent change. Never weaken/remove assertions or change expected results merely to obtain a pass. If a requirement-backed review proves a definition wrong, preserve it, explain the correction, and obtain fresh human approval for the new revision. For a product fix, replay the unchanged approved plan with `npm run execute -- <plan-id> <exact-revision>`; this performs real Playwright execution. Run relevant regression checks (`npm test`, `npm run test:unit`, `npm run test:executor`, or `npm run test:dashboard`) and `npm run typecheck` as appropriate. Port-sharing browser suites must run sequentially. Compare before/after case IDs, revision/hash/approval, commits, expected/actual values, counts, and exit codes; a changed plan is not an unchanged-plan retest.

Record the evidence-backed cause, correction, uncertainty, actual commands/results, and separate failure/retest artifact paths in `docs/AI_WORKFLOW.md`. For deliberately seeded defects, preserve detection evidence before the separate `fix:` commit, as required by `AGENTS.md`.
